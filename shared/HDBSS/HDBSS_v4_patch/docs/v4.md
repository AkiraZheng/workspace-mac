## 0. 目标

当前 DBM 只在热迁移日志阶段才添加 (mmu.c:1965):

```c
if ((*prot & W) && kvm->arch.enable_hdbss && memslot_is_logging(memslot))
    *prot |= KVM_PGTABLE_PROT_DBM;
```

这导致迁移启动时需要一次额外的写 trap: 首次缺页创建 W 页(无DBM) → 迁移WP→ guest 写→ trap→ relax_perms 加 DBM。

目标: 首次缺页创建 W+DBM，迁移时只需 WP 改权限(DBM 原位)，省一次 trap。

改造后的 DBM 条件:

```c
if ((*prot & KVM_PGTABLE_PROT_W) && kvm->arch.enable_hdbss && !s2vi->device)
    *prot |= KVM_PGTABLE_PROT_DBM;
```

移除了 memslot_is_logging 的时间守卫，加 !s2vi->device 显式排除设备页。

## 2. 坑1: 大页粒度 DBM + Lazy Split 导致脏页丢失

### 问题链路

首次缺页 → kvm_pgtable_stage2_map() 创建 2MB 大页 W+DBM
→ 迁移启动修改权限 W+DBM → RO+DBM
→ 大页不 trap(KVM 看不到写),硬件在大页粒度记录 dirty
→ HDBSS buffer 条目: 2MB 基地址 IPA
→ kvm_flush_hdbss_buffer() 只标记 1 个 4KB 页

### 已解决的保护

| 机制 | 位置 | 作用 |
|------|------|------|
| Eager split | mmu.c:1005-1006 | system_supports_hdbss() → split_page_chunk_size=PAGE_SIZE |
| DBM 提取 | pgtable.c:776-777 | kvm_pgtable_stage2_pte_prot() 从父PTE提取DBM |
| DBM 比较 | pgtable.c:788-789 | stage2_pte_needs_update() 检测DBM变化 |
| DBM 继承 | pgtable.c:1548 | stage2_split_walker() 子PTE继承父PTE的DBM |

### 拆页三条路径验证

| 路径 | chunk_size | 涉及函数 | 是否安全 |
|------|:---:|------|:---:|
| 全量拆 | PAGE_SIZE | kvm_mmu_split_memory_region() → kvm_mmu_split_huge_pages() | ✔ |
| 增量拆 | PAGE_SIZE | kvm_arch_mmu_enable_log_dirty_pt_masked() | ✔ |
| Lazy Split | **0** | kvm_mmu_split_huge_pages() 直接 return 0 | ✗ 不适用于HDBSS |

**结论**: HDBSS 场景下 patch 6 已保证 chunk_size != 0，Lazy Split 路径
不可达。但需确保 system_supports_hdbss() 早于 mmu init 执行。

## 3. 坑2: 非迁移场景修改权限时残留 DBM

### 问题

首次缺页加了 W+DBM，但 HDBSS 未启用(或已停用)时，如果其他路径修改页面
权限(W→RO)，DBM 位残留在 PTE 中:

```
RO+DBM = 硬件解释为"跟踪写"，guest 写入时硬件自动升级为 W+DBM(dirty)
       → 不 trap 到 KVM → KVM 无法拦截非法写 → 数据损坏
```

### 需要修改的代码路径

所有修改 S2 PTE 权限的路径，当目标 prot 不含 W 时必须清除 DBM:

```c
// 1. kvm_pgtable_stage2_relax_perms() (pgtable.c:1358+)
//    DBM 已处理 set |= DBM，需要对称加 clr:
if (!(prot & KVM_PGTABLE_PROT_W))
    clr |= KVM_PTE_LEAF_ATTR_HI_S2_DBM;

// 2. stage2_set_prot_attr() (pgtable.c:704+)
//    rebuild ALL bits from prot，需要:
if (!(prot & KVM_PGTABLE_PROT_W))
    attr &= ~KVM_PTE_LEAF_ATTR_HI_S2_DBM;

// 3. kvm_stage2_wp_range() → stage2_attr_walker()
//    需确认 walker 在设置 RO 时同步清除 DBM
```

**注意**: stage2_set_prot_attr 是重建全部属性，如果 prot 不含 DBM→attr
无 DBM，天然正确。但 kvm_pgtable_stage2_relax_perms 是 set/clr 增量修改，
需要显式处理 clr。

## 4. 坑3: 设备页不应加 DBM

### 问题

设备页(VM_PFNMAP/MIXEDMAP + !pfn_is_map_memory) 通过 s2vi->device 标识
(mmu.c:1932)。这些是 MMIO/PASSTHROUGH 地址，不应有 dirty tracking。

当前通过两个条件间接保护:
1. 设备页所在的 memslot 通常 dirty_bitmap==NULL → memslot_is_logging 为 false
2. mmu.c:1960: s2vi->device 短路给 W，但后续仍需 memslot_is_logging 过滤 DBM

但这是间接保护——如果设备所在槽恰好有 dirty_bitmap，当前代码也会给
设备页加 DBM。虽然实际场景中几乎不会发生(设备槽没有 dirty_bitmap)，
但改成首次缺页加 DBM 后条件变为:

```c
if ((*prot & W) && enable_hdbss && !s2vi->device)  // 显式排除
    *prot |= DBM;
```

**显式加 !s2vi->device 替代间接的 memslot_is_logging**。

### memslot_is_logging 当前过滤了什么

| 过滤对象 | 方式 | 可靠性 |
|----------|------|:---:|
| 非迁移普通页 | dirty_bitmap==NULL | 直接 |
| ROM/FW 只读槽 | KVM_MEM_READONLY | 直接 |
| 设备 MMIO 页 | dirty_bitmap 通常 NULL | 间接脆弱 |

去掉 memslot_is_logging 后:
- 非迁移页面加 DBM → 预期行为(todo 目标)
- ROM 页面不加 DBM → 不受影响(ROM 无法获得 W)
- 设备页需 **!s2vi->device** 显式排除

# todo #2 详细分析: 去掉 ioctl + 脏页日志生命周期绑定

## 0. 核心设计

### DBM 与 HDBSS buffer 解耦

| 组件 | 生命周期 | 控制条件 |
|---|---|---|
| S2 PTE 中的 DBM 位 | 首次缺页时设置 (todo #3) | `system_supports_hdbss() && writable && !device` |
| HDBSS per-vCPU buffer | 脏页日志开始时分配，停止时释放 | `kvm->enable_hdbss` |
| VTCR_EL2_HD/HDBSS | 脏页日志开始时设置，停止时清除 | `kvm->enable_hdbss` |

**关键设计**：DBM 位在 VM 启动时就存在于 PTE 中（根据硬件能力），但 VTCR_EL2.HD=0
时 ARM 硬件会忽略 DBM 位——这是 ARM 架构保证的，安全且无副作用。
迁移开始时 enable HDBSS 仅做两件事：分配 buffer + 设置 VTCR bit（DBM 已就位，
不需要扫表添加）。迁移结束时 disable HDBSS 做相反操作：释放 buffer + 清除 VTCR bit
（PTE 中残留的 DBM 被 HD=0 忽略，安全）。

### 为什么必须解耦

原方案 "enable_hdbss 在 VM 启动时置 true，永不关闭" 的代价:
- 每个 vCPU 永久占用 HDBSS buffer（至少 4KB/vCPU）
- 对于从不迁移的 VM，这是纯粹的内存浪费
- 如果后续要支持 buffer size 动态调整（根据 VM 内存大小），需要 disable+re-enable

解耦后 DBM 位仍然在 VM 启动时生成（满足 todo #3 的省 trap 需求），
但 buffer 只在需要用的时候（迁移）才分配。

### 为什么 dirty log stop 路径不可靠

QEMU 的 `memory_global_dirty_log_stop()` 在 VM 不运行时（`!runstate_is_running()`）
会推迟执行，将 stop 注册为 `VMChangeStateEntry` 回调，等待 VM 下次 resume 时执行。

```c
// QEMU system/memory.c:3053
if (!runstate_is_running()) {
    postponed_stop_flags = flags;
    vmstate_change = qemu_add_vm_change_state_handler(...);
    return;  // 推迟！不会走到 do_stop()
}
```

热迁移完成后源端 VM 处于 stopped 状态，这个推迟的 stop 永不被执行。
因此 `KVM_MEM_LOG_DIRTY_PAGES` 不会被清除，`kvm_arch_commit_memory_region`
不会被调用。这就是为什么 disable 路径必须加 `kvm_arch_destroy_vm` 兜底。

## 1. 使能路径: kvm_arch_commit_memory_region

```
QEMU memory_global_dirty_log_start(GLOBAL_DIRTY_MIGRATION)
  → MEMORY_LISTENER_CALL_GLOBAL(log_global_start)
    → flat view rebuild → per-section kvm_log_start()
      → kvm_slot_update_flags() → KVM_SET_USER_MEMORY_REGION
        → 内核: kvm_set_memory_region()
          → nr_memslots_dirty_logging += 1
          → kvm_arch_commit_memory_region(kvm, old, new, change)     ← 钩子点！
```

在 `kvm_arch_commit_memory_region` (mmu.c) 的开头添加检测：

```c
void kvm_arch_commit_memory_region(struct kvm *kvm,
                   struct kvm_memory_slot *old,
                   const struct kvm_memory_slot *new,
                   enum kvm_mr_change change)
{
    bool had_dirty_log = old && (old->flags & KVM_MEM_LOG_DIRTY_PAGES);
    bool has_dirty_log = new && (new->flags & KVM_MEM_LOG_DIRTY_PAGES);

#ifdef CONFIG_ARM64_HDBSS
    /*
     * Auto-enable HDBSS when the first memslot enables dirty logging.
     * Must be BEFORE kvm_mmu_wp_memory_region() so that wp_range
     * preserves DBM already set on PTEs (from todo #3 first-fault).
     */
    if (!had_dirty_log && has_dirty_log && !kvm->enable_hdbss) {
        int order = hdbss_auto_select_order(kvm);
        kvm_arm_hdbss_enable(kvm, order);
    }
#endif

    // ... 原有 write-protect / split 代码 ...

#ifdef CONFIG_ARM64_HDBSS
    /*
     * Auto-disable HDBSS when the last memslot disables dirty logging.
     * nr_memslots_dirty_logging has already been updated by this point
     * (in kvm_commit_memory_region before calling this hook).
     */
    if (had_dirty_log && !has_dirty_log && kvm->enable_hdbss &&
        atomic_read(&kvm->nr_memslots_dirty_logging) == 0)
        kvm_arm_hdbss_disable(kvm);
#endif
}
```

**时序保证**：enable 在 `kvm_mmu_wp_memory_region()` 之前执行，确保：
- 新增映射的页面：`user_mem_abort()` 检测到 `logging_active && enable_hdbss` → 加 DBM
- 已有页面：`wp_range` 只改 AP bits，不碰 DBM → DBM 保留（todo #3 已添加到 PTE）
- 大页拆页：`stage2_split_walker` 已将 DBM 从父 PTE 传递到子 PTE

## 2. 关闭路径 (双重路径)

### 路径 A (正常): dirty log 停止时自动关闭

如果 VM 仍在 running（`runstate_is_running() == true`）:

```
QEMU memory_global_dirty_log_stop()
  → memory_global_dirty_log_do_stop()
    → flat view rebuild → per-section kvm_log_stop()
      → KVM_SET_USER_MEMORY_REGION (flags 清除 LOG_DIRTY_PAGES)
        → kvm_arch_commit_memory_region()
          → had_dirty_log && !has_dirty_log && nr_memslots_dirty_logging == 0
          → kvm_arm_hdbss_disable(kvm)   // 释放所有 vCPU buffer + 清除 VTCR
```

### 路径 B (兜底): VM 销毁时清理

当 VM 迁移完成、源端停止且不再恢复时，dirty log stop 被推迟且永不执行。
HDBSS buffer 保持分配但 VM 已冻结，资源不会被释放直到 VM 销毁。

```c
// arch/arm64/kvm/arm.c:406
void kvm_arch_destroy_vm(struct kvm *kvm)
{
    kvm_sched_affinity_vm_destroy(kvm);     // 现有代码
    // ...
#ifdef CONFIG_ARM64_HDBSS
    if (kvm->enable_hdbss)
        kvm_arm_hdbss_disable(kvm);         // ★ 兜底清理
#endif
    kvm_destroy_vcpus(kvm);                 // 必须在 disable 之后！
    // ...
}
```

**重要**：`kvm_arm_hdbss_disable()` 必须放在 `kvm_destroy_vcpus()` 之前，
因为 disable 函数需要遍历 `kvm_for_each_vcpu` 来释放每个 vCPU 的 buffer 并
kick vCPU。vCPU 销毁后无法遍历。

## 3. per-vCPU 清理路径 (双层防御)

### 第一层: kvm_arm_hdbss_disable() 全局释放

```c
void kvm_arm_hdbss_disable(struct kvm *kvm)
{
    kvm->arch.vtcr &= ~(VTCR_EL2_HD | VTCR_EL2_HDBSS);

    kvm_for_each_vcpu(i, vcpu, kvm) {
        kvm_vcpu_kick(vcpu);
        hdbss_pg = phys_to_page(HDBSSBR_BADDR(vcpu->arch.hdbss.br_el2));
        if (hdbss_pg)
            __free_pages(hdbss_pg, ...);
        vcpu->arch.hdbss.br_el2 = 0;       // ★ 清空指针，防止 double free
        vcpu->arch.hdbss.prod_el2 = 0;
    }

    kvm->enable_hdbss = false;
}
```

设置为 `br_el2 = 0` 后，第二层检查到 0 会跳过。

### 第二层: kvm_arm_vcpu_destroy() per-vCPU 兜底

```c
// reset.c:188 — 已有代码，无需修改
if (vcpu->arch.hdbss.br_el2) {             // 第一层已设为 0 → 跳过
    hdbss_pg = phys_to_page(HDBSSBR_BADDR(vcpu->arch.hdbss.br_el2));
    if (hdbss_pg)
        __free_pages(hdbss_pg, ...);
}
```

如果第一层（全局 disable）因为任何原因被跳过，第二层（per-vCPU destroy）
仍会通过 `kvm_destroy_vcpus() → kvm_arm_vcpu_destroy()` 逐个释放 buffer。
不会 double free，因为第一层成功执行后 `br_el2 = 0`。

## 0. 目标
<br/>
确认 HDBSS buffer 在所有 VM 生命周期路径下都能被正确释放，不存在内存泄漏。

## 4. Double Free 分析
<br/>
`kvm_arm_hdbss_disable()` 中的关键序列：
```
for each vcpu:
    __free_pages(hdbss_pg, order);   // 释放 buffer
    vcpu->arch.hdbss.br_el2 = 0;     // ★ 设空指针
```
<br/>
之后 `kvm_arm_vcpu_destroy()` (reset.c:188):
```
if (vcpu->arch.hdbss.br_el2) {       // 0 → 跳过
    __free_pages(...);               // 不会调用
}
```
<br/>
**结论**: `br_el2 = 0` 作为 guard 防止 double free。
全局释放先执行 → 设空指针 → per-vCPU 释放检查到空指针 → 跳过。
<br/>
## 5. 泄漏判定: 不存在
<br/>
| 场景 | 最终触达的释放点 | 是否泄漏 |
|---|---|---|
| 迁移完成(VM running) → dirty log stop | F1 | ✗ |
| 迁移完成(VM stopped) → VM 恢复 → stop | F1 | ✗ |
| 迁移完成(VM stopped) → VM 销毁 | F2 + F3(跳过) | ✗ |
| 迁移完成(VM stopped) → 再次迁移 → 最终销毁 | F2 + F3(跳过) | ✗ |
| 迁移失败 → 异常退出 | F2 + F3(跳过) | ✗ |
| vCPU 热拔 (迁移期间) | F4 | ✗ |
| enable 时分配失败回滚 | F5 + F4 | ✗ |
| **{VM stopped 且永不被销毁}** | **永不释放** | **N/A (VM 状态冻结)** |
<br/>
**唯一不释放的场景**: 源端 VM 迁移完成后 QEMU 进程既不销毁也不恢复 VM。
此场景下 VM 已停止，vCPU 不再运行，HDBSS buffer 虽占用但无新分配，且 VM
的生命周期最终必然走到销毁（QEMU 退出时 close fd 或 kill 进程）。
这不算内存泄漏——所有分配的内存仍可被追踪，且最终会被 F2 释放。
<br/>
## 6. kvm_vcpu_release() 路径分析
<br/>
```c
// kvm_main.c:3986
static int kvm_vcpu_release(struct inode *inode, struct file *filp)
{
    kvm_put_kvm(vcpu->kvm);  // 只减引用计数
    return 0;
}
```
<br/>
`kvm_vcpu_release()` 仅递减 `kvm->users_count`，不直接调用
`kvm_vcpu_destroy()`。vCPU 结构的实际销毁在 `kvm_destroy_vcpus()` 中
统一执行（由 `kvm_arch_destroy_vm()` 触发）。因此单 vCPU fd close
不会触发 HDBSS buffer 的 per-vCPU 释放——只有 VM 销毁时才会。
<br/>
但 per-vCPU 释放（F3/F4）作为第二层防御仍然存在：如果第一层（F1/F2）失败，
`kvm_destroy_vcpus()` 中对每个 vCPU 调用 `kvm_arm_vcpu_destroy()` 时会
检查 `br_el2 != 0` 并释放，确保没有泄漏。

# 热插拔风险分析

## 场景真实性

vCPU 热插拔在 KVM API 层面完全合法: `KVM_CREATE_VCPU` 可在任意时刻
调用（受 `kvm->lock` 保护）。QEMU 通过 QMP `device_add` 可动态添加 vCPU。
不过实际生产环境中 libvirt 通常锁定拓扑，热迁移期间不会执行热插拔。

更准确的问题表述: **一旦 `enable_hdbss` 设好, 任何后续 vCPU 创建（无论
正常启动的第 2 个 vCPU 还是热插拔的第 N 个）都必须独立分配 buffer。**
这也正是上述方案中拆分 `hdbss_alloc_vcpu_buffer` 的原因。

## 分配失败的正确行为

热插拔 vCPU 若 buffer 分配失败:

```
方案 A (正确): kvm_arch_vcpu_create 返回 -ENOMEM
              → kvm_vm_ioctl_create_vcpu 返回 err
              → QEMU 收到错误, vCPU 创建失败
              → 其他 vCPU 不受影响, VM 继续正常运行
              → HDBSS 保持启用

方案 B (错误): disable HDBSS + 清除所有 DBM 位
              → clear VTCR_EL2_HD/HDBSS/HA
              → 遍历所有 S2 页表逐 PTE clear DBM (百万级)
              → 暂停所有在线 vCPU (stop + synchronize)
              → 释放所有已有 vCPU 的 buffer
              → 通知 QEMU dirty tracking 退化到纯软件
              → 下次迁移必须在默认路径重加 DBM (额外 trap)
```

代价对比:

| | 方案 A | 方案 B |
|---|:---:|:---:|
| 受影响 vCPU | 1 个 (创建失败) | 全部 (暂停扫表) |
| 是否需要扫页表 | 否 | 是 (百万 PTE) |
| 迁移连续性 | 不受影响 | 退化 + 重建 |

**结论: 分配失败只终止当前 vCPU 创建，绝不 disable HDBSS。**

## 热拔路径 (vCPU destroy)

```c
// reset.c:165 — 已正确处理
if (vcpu->kvm->arch.enable_hdbss)
    kvm_arm_vcpu_free_hdbss(vcpu);
```

销毁 vCPU 时释放其 buffer，无需额外改动。

## 设计原则

1. HDBSS 一旦启用，VM 生命周期内永不关闭
2. 热插拔只需分配 buffer + 填充 vcpu->arch.hdbss，失败退 -ENOMEM
3. 热拔只需 free buffer，现有代码已覆盖
4. disable HDBSS = 全量扫表 clear DBM，绝不作为错误恢复路径

## 2. 方案选择：Request vs 直接 Flush

### 方案 A: 直接 flush (当时就执行)

```c
void kvm_arch_vcpu_put(struct kvm_vcpu *vcpu)
{
    ...
    kvm_vcpu_put_vhe(vcpu);
    kvm_flush_hdbss_buffer(vcpu);  // ← 在 kvm_arch_vcpu_put 中直接 flush
    ...
}
```

| 优点 | 缺点 |
|------|------|
| flush 立即完成 | `kvm_sched_out` 中拿 mmu_lock 有调度器上下文风险 |
| 代码简单 | 每次 vcpu_put/sched_out 都执行，即使 buffer 为空 |
| — | 与 Marc "不过度调用" 的要求相悖 |

### 方案 B: Request (延迟到安全点) ★ 推荐

```c
void kvm_arch_vcpu_put(struct kvm_vcpu *vcpu)
{
    ...
    kvm_vcpu_put_vhe(vcpu);                          // 纯寄存器操作
    if (kvm->arch.enable_hdbss)
        kvm_make_request(KVM_REQ_FLUSH_HDBSS, vcpu);  // 标记需要 flush
    ...
}
```

实际 flush 在 vCPU 下次被 load 并退出 guest 时执行：

```c
// arm.c — check_vcpu_requests (已有代码，无需修改)
if (kvm_check_request(KVM_REQ_FLUSH_HDBSS, vcpu))
    kvm_flush_hdbss_buffer(vcpu);
```

| 优点 | 缺点 |
|------|------|
| `kvm_vcpu_put_vhe` 保持轻量（纯寄存器） | flush 稍有延迟 |
| 不在调度器路径中拿锁，安全 | — |
| 只在 enable_hdbss 时才 set request，无谓开销 | — |
| 复用已有 `KVM_REQ_FLUSH_HDBSS` 机制，一致性强 | — |
| 符合 KVM 中 `KVM_REQ_TLB_FLUSH` 等 request 的设计模式 | — |

### 选择: 方案 B — Request

**理由**:
1. **锁安全**: `kvm_sched_out` 来自调度器，不在此上下文中拿 `mmu_lock`
2. **一致性**: `KVM_REQ_FLUSH_HDBSS` 已被 `kvm_arch_sync_dirty_log` 使用
3. **Marc 的要求**: 仅在需要时执行（空 buffer 时 `curr_idx == 0` 快速返回）
4. **架构干净**: 分离关注点，put 不影响 flush 语义

### 3.3 保留: `check_vcpu_requests` 中的 flush 处理 (无需改动)

```c
// arm.c — 已有代码
if (kvm_check_request(KVM_REQ_FLUSH_HDBSS, vcpu))
    kvm_flush_hdbss_buffer(vcpu);
```

### 3.4 fault handler 同样改用 request

`kvm_handle_hdbss_fault` 中也不应直接 flush（IRQ 上下文，与 vcpu_put 同理）：

```c
// mmu.c — kvm_handle_hdbss_fault
case HDBSSPROD_EL2_FSC_OK:
-   kvm_flush_hdbss_buffer(vcpu);                  // 直接 flush (在 IRQ 中拿锁)
-   return 1;
+   kvm_make_request(KVM_REQ_FLUSH_HDBSS, vcpu);   // set request, 安全点执行
+   return 1;
```

## 4. 完整 Flush 触发点 (v4)

| # | 触发点 | 机制 | 时机 |
|---|--------|------|------|
| 1 | `kvm_arch_vcpu_put` | **set request** → `check_vcpu_requests` | vCPU 被调度出去 / put |
| 2 | `kvm_arch_sync_dirty_log` | `kvm_make_all_cpus_request(KVM_REQUEST_WAIT)` | 主动同步 dirty bitmap |
| 3 | `kvm_handle_hdbss_fault` | **set request** → `check_vcpu_requests` | HDBSSF buffer full |

**统一原则**: 所有触发点只负责 `kvm_make_request`，实际的 `kvm_flush_hdbss_buffer`
只在 `check_vcpu_requests` 中执行（安全的进程上下文，已获取 mmu_lock）。
