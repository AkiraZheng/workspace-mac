# todo #3 详细分析: 首次缺页自动加DBM

## 0. 目标

当前 DBM 只在热迁移日志阶段才添加 (mmu.c:1965):

```c
if ((*prot & W) && kvm->arch.enable_hdbss && memslot_is_logging(memslot))
    *prot |= KVM_PGTABLE_PROT_DBM;
```

这导致迁移启动时需要一次额外的写 trap: 首次缺页创建 W 页(无DBM) → 迁移WP→ guest 写→ trap→ relax_perms 加 DBM。

目标: 首次缺页创建 W+DBM，迁移时只需 WP 改权限(DBM 原位)，省一次 trap。

改造后的 DBM 条件:

```c
if ((*prot & KVM_PGTABLE_PROT_W) && kvm->arch.enable_hdbss && !s2vi->device)
    *prot |= KVM_PGTABLE_PROT_DBM;
```

移除了 memslot_is_logging 的时间守卫，加 !s2vi->device 显式排除设备页。

- 接口: 复用已实现的 kvm_arm_enable_hdbss_internal(kvm, order)

ioctl 移到 memslot 创建路径), arm.c (去掉 ioctl 复杂逻辑，保留薄封装)

## 2. 坑1: 大页粒度 DBM + Lazy Split 导致脏页丢失

### 问题链路

首次缺页 → kvm_pgtable_stage2_map() 创建 2MB 大页 W+DBM
→ 迁移启动修改权限 W+DBM → RO+DBM
→ 大页不 trap(KVM 看不到写),硬件在大页粒度记录 dirty
→ HDBSS buffer 条目: 2MB 基地址 IPA
→ kvm_flush_hdbss_buffer() 只标记 1 个 4KB 页

### 已解决的保护

| 机制 | 位置 | 作用 |
|------|------|------|
| Eager split | mmu.c:1005-1006 | system_supports_hdbss() → split_page_chunk_size=PAGE_SIZE |
| DBM 提取 | pgtable.c:776-777 | kvm_pgtable_stage2_pte_prot() 从父PTE提取DBM |
| DBM 比较 | pgtable.c:788-789 | stage2_pte_needs_update() 检测DBM变化 |
| DBM 继承 | pgtable.c:1548 | stage2_split_walker() 子PTE继承父PTE的DBM |

### 拆页三条路径验证

| 路径 | chunk_size | 涉及函数 | 是否安全 |
|------|:---:|------|:---:|
| 全量拆 | PAGE_SIZE | kvm_mmu_split_memory_region() → kvm_mmu_split_huge_pages() | ✔ |
| 增量拆 | PAGE_SIZE | kvm_arch_mmu_enable_log_dirty_pt_masked() | ✔ |
| Lazy Split | **0** | kvm_mmu_split_huge_pages() 直接 return 0 | ✗ 不适用于HDBSS |

**结论**: HDBSS 场景下 patch 6 已保证 chunk_size != 0，Lazy Split 路径
不可达。但需确保 system_supports_hdbss() 早于 mmu init 执行。

## 3. 坑2: 非迁移场景修改权限时残留 DBM

### 问题

首次缺页加了 W+DBM，但 HDBSS 未启用(或已停用)时，如果其他路径修改页面
权限(W→RO)，DBM 位残留在 PTE 中:

```
RO+DBM = 硬件解释为"跟踪写"，guest 写入时硬件自动升级为 W+DBM(dirty)
       → 不 trap 到 KVM → KVM 无法拦截非法写 → 数据损坏
```

### 需要修改的代码路径

所有修改 S2 PTE 权限的路径，当目标 prot 不含 W 时必须清除 DBM:

```c
// 1. kvm_pgtable_stage2_relax_perms() (pgtable.c:1358+)
//    DBM 已处理 set |= DBM，需要对称加 clr:
if (!(prot & KVM_PGTABLE_PROT_W))
    clr |= KVM_PTE_LEAF_ATTR_HI_S2_DBM;

// 2. stage2_set_prot_attr() (pgtable.c:704+)
//    rebuild ALL bits from prot，需要:
if (!(prot & KVM_PGTABLE_PROT_W))
    attr &= ~KVM_PTE_LEAF_ATTR_HI_S2_DBM;

// 3. kvm_stage2_wp_range() → stage2_attr_walker()
//    需确认 walker 在设置 RO 时同步清除 DBM
```

**注意**: stage2_set_prot_attr 是重建全部属性，如果 prot 不含 DBM→attr
无 DBM，天然正确。但 kvm_pgtable_stage2_relax_perms 是 set/clr 增量修改，
需要显式处理 clr。

## 4. 坑3: 设备页不应加 DBM

### 问题

设备页(VM_PFNMAP/MIXEDMAP + !pfn_is_map_memory) 通过 s2vi->device 标识
(mmu.c:1932)。这些是 MMIO/PASSTHROUGH 地址，不应有 dirty tracking。

当前通过两个条件间接保护:
1. 设备页所在的 memslot 通常 dirty_bitmap==NULL → memslot_is_logging 为 false
2. mmu.c:1960: s2vi->device 短路给 W，但后续仍需 memslot_is_logging 过滤 DBM

但这是间接保护——如果设备所在槽恰好有 dirty_bitmap，当前代码也会给
设备页加 DBM。虽然实际场景中几乎不会发生(设备槽没有 dirty_bitmap)，
但改成首次缺页加 DBM 后条件变为:

```c
if ((*prot & W) && enable_hdbss && !s2vi->device)  // 显式排除
    *prot |= DBM;
```

**显式加 !s2vi->device 替代间接的 memslot_is_logging**。

### memslot_is_logging 当前过滤了什么

| 过滤对象 | 方式 | 可靠性 |
|----------|------|:---:|
| 非迁移普通页 | dirty_bitmap==NULL | 直接 |
| ROM/FW 只读槽 | KVM_MEM_READONLY | 直接 |
| 设备 MMIO 页 | dirty_bitmap 通常 NULL | 间接脆弱 |

去掉 memslot_is_logging 后:
- 非迁移页面加 DBM → 预期行为(todo 目标)
- ROM 页面不加 DBM → 不受影响(ROM 无法获得 W)
- 设备页需 **!s2vi->device** 显式排除

## 5. 坑4: 脏页计数标记不匹配

### 问题 (mmu.c:2069-2072)

kvm_s2_fault_map() 在映射成功后调用 mark_page_dirty_in_slot() 标记整个

# todo #2 详细分析: 去掉 ioctl + 自动使能

## 0. 为什么必须去掉 ioctl

当前 HDBSS 启停依赖 QEMU 在迁移起止时调用 ioctl:

```c
// QEMU ram.c
kvm_update_hdbss_cap(true, size);   // 迁移开始 → ioctl enable
memory_global_dirty_log_start();
...
kvm_update_hdbss_cap(false, 0);     // 迁移结束 → ioctl disable
```

但若实现 todo #3（首次缺页加 DBM），`enable_hdbss` 必须在首次缺页
之前即为 true。首次缺页发生在 VM 刚启动、vCPU 刚开始运行 guest 代码
时——远早于迁移。所以必须把 HDBSS 使能从"等 ioctl"改为"VM 创建时自动"。

## 1. 使能时机: kvm_arch_vcpu_create

QEMU 初始化顺序: KVM_CREATE_VM → KVM_SET_USER_MEMORY_REGION×N → KVM_CREATE_VCPU×N → KVM_RUN

选择 `kvm_arch_vcpu_create` 作为使能点:
- 此时所有 memslot 已创建 → hdbss_auto_select_order() 能统计总页数
- 此时 vCPU 尚未运行 guest 代码 → 首次缺页还没发生
- 早于任何页面创建 → DBM 可在首次映射时立即写入

## 2. 核心问题: kvm_arm_enable_hdbss_internal 的缺陷

该函数当前实现 (dirty_bit.c:62):

```c
if (kvm->arch.enable_hdbss)
    return 0;   // 已启用→直接返回, 不给后续 vCPU 分配 buffer!
```

**后果**: 第一个 vCPU 创建时调用 enable_internal → 只为 vCPU 0 分配 buffer →
设 flag。第二个及后续 vCPU（无论正常启动还是热插拔）调用时 flag 已为 true →
直接 return 0 → **后创建的 vCPU 没有 buffer** → kvm_load_hdbss 写 0 到
HDBSSBR_EL2 → 硬件把脏页记录写到地址 0 → 系统崩溃。

## 3. 方案: 拆分 per-vCPU buffer 分配

新增 per-vCPU 分配函数:

```c
// dirty_bit.c — 只为单个 vCPU 分配 HDBSS buffer
static int hdbss_alloc_vcpu_buffer(struct kvm_vcpu *vcpu, unsigned int order)
{
    struct page *pg = alloc_pages(GFP_KERNEL_ACCOUNT, order);
    if (!pg)
        return -ENOMEM;
    vcpu->arch.hdbss = (struct vcpu_hdbss_state){
        .base_phys = page_to_phys(pg),
        .hdbssbr_el2 = HDBSSBR_EL2(page_to_phys(pg), order),
        .hdbssprod_el2 = 0,
    };
    return 0;
}
```

在 `kvm_arch_vcpu_create` 中调用:

```c
// arm.c:543 — vCPU 创建时
int kvm_arch_vcpu_create(struct kvm_vcpu *vcpu)
{
    ...
    if (system_supports_hdbss()) {
        unsigned int order = hdbss_auto_select_order(vcpu->kvm);
        int ret;

        if (!vcpu->kvm->arch.enable_hdbss) {
            // 第一个 vCPU: 全局使能 + 自身 buffer
            ret = kvm_arm_enable_hdbss_internal(vcpu->kvm, order);
        } else {
            // 后续 vCPU / 热插拔: 只分配自身 buffer
            ret = hdbss_alloc_vcpu_buffer(vcpu, order);
        }
        if (ret)
            return ret;
    }
    ...
}
```

## 4. HDBSS 生命周期: 只开不关

HDBSS 在 VM 生命周期内**永不关闭**。即使迁移结束 dirty logging 停止，
HDBSS 仍然运行:

```
VM boot → vCPU 创建 → enable_hdbss=true → 首次缺页加 DBM
         ↓
普通运行 → DBM 保持, HDBSS buffer 持续记录 (被 vcpu_put 异步冲入 bitmap, 无害)
         ↓
迁移开始 → dirty logging 启用 → DBM 已有, buffer 记录被 sync 获取 ✓
         ↓
迁移结束 → dirty logging 停止 → HDBSS 继续运行, DBM 保持
         ↓
VM 销毁 → kvm_arch_destroy_vm → 释放所有 buffer
```

为什么不能 disable: 关闭 HDBSS 需要 clear VTCR_EL2_HD/HDBSS/HA +
遍历所有 S2 页表清除 DBM 位（可能百万级 PTE）+ 暂停所有 vCPU。代价
远大于让 HDBSS 空闲运行。ARM 规范保证 VTCR_EL2.HD=1 时硬件正常管理 DBM，
即使没有 dirty logging 消费者也无副作用。

## 5. 销毁路径: VM 和 vCPU

```c
// arm.c — destroy_vm，在所有 vCPU 释放前

```

## 6. ioctl 兼容: 改为 no-op

QEMU 仍然调用 `kvm_update_hdbss_cap(true/false, size)`，内核端：

```c

static int kvm_cap_arm_enable_hdbss(struct kvm *kvm,
                    struct kvm_enable_cap *cap)

```

`KVM_CAP_ARM_HW_DIRTY_STATE_TRACK` 仍返回 0 而不是 -EINVAL，QEMU 不用改。

## 7. size 自动选择

QEMU 原本传 `migrate_hdbss_buffer_size()`，内核改为 `hdbss_auto_select_order()`:

```c
// dirty_bit.c — 按 VM 总页数选 buffer 级别
unsigned int hdbss_auto_select_order(struct kvm *kvm)
{
    // 统计所有 memslot 的 npages
    if (npages <= 16384)    return 0;  // 4KB  (≤64MB VM)
    else if (npages <= 262144) return 3;  // 32KB (≤1GB VM)
    else if (npages <= 4194304) return 6;  // 256KB (≤16GB VM)
    else                   return 9;   // 2MB  (>16GB VM)
}
```

# 热插拔风险分析

## 场景真实性

vCPU 热插拔在 KVM API 层面完全合法: `KVM_CREATE_VCPU` 可在任意时刻
调用（受 `kvm->lock` 保护）。QEMU 通过 QMP `device_add` 可动态添加 vCPU。
不过实际生产环境中 libvirt 通常锁定拓扑，热迁移期间不会执行热插拔。

更准确的问题表述: **一旦 `enable_hdbss` 设好, 任何后续 vCPU 创建（无论
正常启动的第 2 个 vCPU 还是热插拔的第 N 个）都必须独立分配 buffer。**
这也正是上述方案中拆分 `hdbss_alloc_vcpu_buffer` 的原因。

## 分配失败的正确行为

热插拔 vCPU 若 buffer 分配失败:

```
方案 A (正确): kvm_arch_vcpu_create 返回 -ENOMEM
              → kvm_vm_ioctl_create_vcpu 返回 err
              → QEMU 收到错误, vCPU 创建失败
              → 其他 vCPU 不受影响, VM 继续正常运行
              → HDBSS 保持启用

方案 B (错误): disable HDBSS + 清除所有 DBM 位
              → clear VTCR_EL2_HD/HDBSS/HA
              → 遍历所有 S2 页表逐 PTE clear DBM (百万级)
              → 暂停所有在线 vCPU (stop + synchronize)
              → 释放所有已有 vCPU 的 buffer
              → 通知 QEMU dirty tracking 退化到纯软件
              → 下次迁移必须在默认路径重加 DBM (额外 trap)
```

代价对比:

| | 方案 A | 方案 B |
|---|:---:|:---:|
| 受影响 vCPU | 1 个 (创建失败) | 全部 (暂停扫表) |
| 是否需要扫页表 | 否 | 是 (百万 PTE) |
| 迁移连续性 | 不受影响 | 退化 + 重建 |

**结论: 分配失败只终止当前 vCPU 创建，绝不 disable HDBSS。**

## 热拔路径 (vCPU destroy)

```c
// reset.c:165 — 已正确处理
if (vcpu->kvm->arch.enable_hdbss)
    kvm_arm_vcpu_free_hdbss(vcpu);
```

销毁 vCPU 时释放其 buffer，无需额外改动。

## 设计原则

1. HDBSS 一旦启用，VM 生命周期内永不关闭
2. 热插拔只需分配 buffer + 填充 vcpu->arch.hdbss，失败退 -ENOMEM
3. 热拔只需 free buffer，现有代码已覆盖
4. disable HDBSS = 全量扫表 clear DBM，绝不作为错误恢复路径
