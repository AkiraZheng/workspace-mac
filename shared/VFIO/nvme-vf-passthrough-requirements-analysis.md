| 项目 | 内容 |
|------|------|
| 文档编号 | TECH-DEC-2026-001 |
| 归档日期 | 2026-07-08 |
| 文档版本 | V1.0 |
| 涉及团队 | 虚拟化平台团队 / PCIe硬件团队 / 产品团队 |

## 一、背景与问题描述

### 1.1 问题触发

在NVMe VF直通测试中发现，普通虚拟机直通VF后未正常退出，宿主机环境重启后再次直通该VF时，VF报FLR（Function Level Reset）错误。初步怀疑与NVMe VF资源分配/状态残留有关。

### 1.2 现有规避措施

当前自动化测试脚本在每次用例结束后会强制杀掉QEMU进程，因此该问题在常规CI/CD流程中未被暴露。这属于掩盖问题而非解决问题。

### 1.3 争议点

- PCIe团队反馈：NVMe VF不在其验收范围，无相关需求
- 虚拟化团队疑问：机密虚机、部分产品线可能涉及NVMe VF使用场景，责任归属模糊
- 产品侧未明确是否需要对外提供该能力

## 二、技术方案梳理

### 2.1 相关技术方案定义

| 方案 | 本质 | 是否直通 | 是否依赖SR-IOV | 数据路径 |
|------|------|----------|-----------------|----------|
| virtio-blk | 半虚拟化软件方案 | 否 | 否 | VM → virtqueue → 宿主机内核 → 存储设备 |
| vhost-user-blk | 半虚拟化软件方案（用户态后端） | 否 | 否 | VM → virtqueue → 用户态后端 → 存储设备 |
| vfio-pci (PF直通) | 硬件直通方案 | 是 | 否 | VM驱动 → 直接操作硬件寄存器 → 物理设备 |
| vfio-pci (VF直通) | 硬件直通方案 | 是 | 是 | VM驱动 → 直接操作VF寄存器 → 物理设备 |

### 2.2 存储部署架构与方案映射

| 存储位置 | 典型场景 | 使用的技术方案 | 是否需要VF直通 |
|----------|----------|----------------|-----------------|
| 远端存储池 | 分布式存储（Ceph）、SAN、NVMe-oF | virtio-blk / vhost-user-blk | 否 |
| 本地直连存储（非直通） | 宿主机本地盘，普通虚机使用 | virtio-blk（后端指向本地文件/块设备） | 否 |
| 本地直连存储（直通） | 高性能数据库、机密虚机 | vfio-pci（PF或VF直通） | 是 |

### 2.3 方案选型本质

方案选型的核心是 **性能与灵活性的权衡**：

- **virtio-blk**：软件定义，不挑硬件，稳定通用，管理简单，但存在少量Hypervisor介入开销
- **vfio-pci (SR-IOV VF直通)**：追求接近裸金属的极致性能，数据流绕过Hypervisor，但强依赖硬件SR-IOV能力，且VF状态管理（FLR、资源回收）复杂

## 三、场景与需求评估

### 3.1 产品侧使用场景分析

| 场景类型 | 是否涉及NVMe VF直通 | 说明 |
|----------|---------------------|------|
| 普通虚机（通用计算） | 否 | virtio-blk性能已满足，无需直通 |
| 高性能数据库节点 | 按需 | 仅极少数对延迟有极致SLA要求的场景 |
| AI/ML训练节点（本地缓存） | 按需 | 部分场景有本地高速盘需求，但可用PF直通替代 |
| 机密虚机（安全隔离） | 待确认 | 需绕过宿主机减少攻击面，但需求方未明确具体要求 |
| 裸金属服务器 | 否 | PF直通已覆盖，不涉及VF |

**关键判断依据**：

1. 当前主流存储趋势为分布式、池化、远端化（Ceph、vSAN、NVMe-oF），虚拟机存储访问主要走网络协议栈，本地NVMe盘并非核心路径
2. 本地NVMe盘仍有应用场景（如高性能数据库redo log、AI训练缓存盘），但占比相对有限
3. 即使需要本地盘独占，PF直通已可覆盖单盘独占场景，VF直通的"一虚多"能力需求不明确

### 3.2 技术维护成本评估

| 评估维度 | virtio-blk | vfio-pci VF直通 |
|----------|------------|-----------------|
| 性能水平 | 优秀（约90%裸金属） | 极致（约99%裸金属） |
| 硬件依赖 | 无 | 强依赖（SSD需支持SR-IOV，PCIe ACS等） |
| 已知问题复杂度 | 低 | 高（FLR、VF状态残留、资源回收、中断路由等） |
| 问题定位难度 | 低 | 高（涉及硬件行为、PCIe规范、内核VFIO框架） |
| 跨团队协调成本 | 低 | 高（需硬件/PCIe/虚拟化/内核多方协同） |
| 回归测试成本 | 低 | 高（需覆盖多种SSD型号、固件版本、宿主机配置） |

### 3.3 已知技术风险

1. **FLR状态残留**：VF直通后未正常退出，宿主机重启后再次直通报FLR错误，根因与NVMe VF资源分配/状态管理有关
2. **VF资源回收**：QEMU异常退出时VF资源未正确释放，影响后续分配
3. **硬件兼容性**：不同SSD厂商的SR-IOV实现行为存在差异，需逐型号验证

## 四、调研结论

### 4.1 综合判断

| 维度 | 结论 |
|------|------|
| 业务趋势 | 存储向分布式、远端化发展，本地直通场景占比低 |
| 技术替代性 | virtio-blk可覆盖绝大多数场景性能需求，PF直通可覆盖本地盘独占需求 |
| 维护成本 | VF直通维护成本显著高于收益（FLR等问题需跨团队协同定位） |
| 责任边界 | PCIe团队明确不验NVMe VF，责任归属模糊易导致问题推诿 |

### 4.2 建议决策

**建议选择：不将NVMe VF直通作为通用能力维护**

- NVMe VF直通定位为技术储备，不作为产品基线能力
- 机密虚机等特殊场景如有明确需求，走独立项目评审流程，按定制化需求支持
- 虚拟化平台团队不对NVMe VF直通问题进行主动修复

**如存在特定产品线明确需求，备选方案：保留NVMe VF直通作为特定场景可选能力**

- 仅限已确认的产品线/场景使用，需明确客户/项目名称
- PCIe/硬件团队主导VF状态问题（含FLR），虚拟化团队负责VFIO框架适配层
- 需明确VF直通支持的具体硬件型号、固件版本清单

## 五、责任划分建议

| 角色 | 责任范围 |
|------|----------|
| 产品团队 | 明确客户场景需求，提出功能需求并评估商业价值 |
| 虚拟化平台团队 | 维护virtio-blk/vhost-user-blk方案，保障通用场景存储性能；提供VFIO框架适配能力 |
| PCIe/硬件团队 | 负责SR-IOV VF硬件行为（含FLR、状态重置、资源回收）问题定位与修复 |
| 测试团队 | 覆盖已声明支持的硬件组合及场景的回归测试 |

## 六、闭环机制

1. 本决策文档经相关团队评审签字后生效，作为后续NVMe VF直通相关问题的判断依据
2. 涉及NVMe VF直通的新问题单，由问题提出方先查阅本文档确定支持范围：
   - 在支持范围内的 → 按责任划分分配处理
   - 不在支持范围内的 → 关闭或转为需求评审
3. 本决策每12个月或当产品路线图发生重大变化时重新评估

## 七、调研执行计划

### 阶段一：需求侧拉通（第1-2周）

**目标：确认"有没有人真正需要NVMe VF直通"**

| 序号 | 行动 | 对接方 | 需确认的关键问题 | 产出 |
|------|------|--------|-------------------|------|
| 1.1 | 产品线需求访谈 | 产品经理 | 当前哪些产品/客户明确要求NVMe VF直通能力？是否有已签约项目依赖该特性？ | 需求清单及优先级 |
| 1.2 | 机密虚机团队访谈 | 机密计算架构师 | 机密虚机存储访问是否必须绕过宿主机？virtio-blk后端在宿主机的可见性是否构成安全威胁？能否用PF直通替代VF直通？ | 机密虚机场景结论 |
| 1.3 | 存储架构团队访谈 | 存储架构师 | 当前产品主流部署是远端存储还是本地盘？本地盘场景中，单盘独占（PF直通）是否够用，是否真的需要一虚多（VF直通）？ | 存储架构趋势结论 |
| 1.4 | 性能团队访谈 | 性能测试工程师 | 现有virtio-blk/vhost-user-blk在典型业务（数据库、AI）下的性能数据？是否有业务因virtio-blk性能不足而受阻？ | 性能对比数据 |

**阶段一完成标准**：获得以下任一结论——

- 明确无产品线需要VF直通 → 直接跳至阶段四，决策为"不维护"
- 有产品线明确需要 → 继续阶段二

### 阶段二：技术可行性深挖（第3-4周）

**目标：确认"如果要做，代价有多大"**

| 序号 | 行动 | 对接方 | 需确认的关键问题 | 产出 |
|------|------|--------|-------------------|------|
| 2.1 | FLR问题根因分析 | PCIe/硬件团队 | FLR报错的根因是什么？是硬件行为还是内核VFIO驱动问题？修复工作量预估？ | FLR根因分析及修复评估 |
| 2.2 | VF资源回收机制分析 | 内核/虚拟化团队 | QEMU异常退出时VF资源未释放的具体路径？内核层面能否自动回收？需改动哪些子系统？ | 资源回收修复方案及工作量 |
| 2.3 | 硬件兼容性摸底 | PCIe/硬件团队 | 当前支持NVMe SR-IOV的SSD型号有哪些？不同厂商实现差异多大？是否需要逐型号适配？ | 硬件兼容性矩阵 |
| 2.4 | 替代方案评估 | 虚拟化团队 | PF直通能否满足阶段一确认的需求？vhost-user-blk + SPDK能否在性能上接近直通从而替代VF方案？ | 替代方案可行性结论 |

**阶段二完成标准**：获得以下结论——

- FLR等问题的修复工作量及责任人
- 替代方案（PF直通/vhost-user-blk）是否可满足需求
- 如需维护，需投入的人力估算

### 阶段三：决策评审（第5周）

**目标：基于前两阶段结论，形成最终决策**

| 序号 | 行动 | 对接方 | 需确认的关键问题 | 产出 |
|------|------|--------|-------------------|------|
| 3.1 | 编写调研结论补充报告 | 自身 | 将阶段一、二结论填入本报告第四章"调研结论" | 补充完整的调研报告 |
| 3.2 | 组织决策评审会 | 虚拟化/PCIe/产品/机密虚机各团队负责人 | 基于数据做出最终决策：维护/不维护/有限维护 | 会议纪要 |
| 3.3 | 签字确认 | 各团队负责人 | 对决策结论和责任划分签字确认 | 签字版归档文档 |

### 阶段四：归档闭环（第6周）

**目标：将决策固化为正式文档，完成闭环**

| 序号 | 行动 | 产出 |
|------|------|------|
| 4.1 | 将签字版决策文档归档至团队知识库 | 归档文档 |
| 4.2 | 通知相关团队决策结论及后续问题单处理流程 | 邮件通知 |
| 4.3 | 如决策为"不维护"，关闭相关未解决问题单 | 问题单状态更新 |
| 4.4 | 如决策为"有限维护"，明确支持范围并同步测试团队 | 测试范围文档 |

### 决策判定流程图

```
阶段一：需求侧拉通
    │
    ├─→ 无产品线需要VF直通 ─────────────────────→ 不维护（归档）
    │
    └─→ 有产品线明确需要
            │
            ├─→ PF直通可替代 ──→ 推荐PF直通，不维护VF ──→ 不维护VF（归档）
            │
            └─→ PF直通不可替代，必须VF
                    │
                    ├─→ FLR等问题可修复且工作量可控 ──→ 有限维护（明确范围和责任）
                    │
                    └─→ FLR等问题修复代价过高 ──→ 升级决策（上报管理层）或有限维护（带风险说明）
```
