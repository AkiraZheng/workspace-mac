harness主张:模型能力是概率的,会漂移的,偶尔会失控,真正让agent可用,可控,可演化的,是模型外面那一层工程化的骨架(harness):
- 结构化的上下文
- 约束性的工具协议
- 生命周期的钩子
- 可恢复的状态
- 可观测的评估(每个完整任务有workspace级别的id,每个patch有自己的traceID)

- 为什么需要harness来约束?
	- 一个新session启动后,它相当于一个新大脑,如果不做约束,你会发现它的行为很发散.于是我们用SKILL.md来约束它,但是如果只有纯文本,你会发现,AI虽然能通过你在SKILL中定好的规则,少走一些弯路,但是新的问题出现了,prompt写得再好也难以穷尽所有隐式规则(命名规范,逻辑约定,边界处理),而且再强的模型,也会有context上下文窗口约束,目前GLM5.2,DS已经能支持最大1M的上下文了,其实已经够用了,但是还是无法避免挤爆上下文的问题.而且并不是所有模型都有大上下文,有了harness,就能允许我们在低价的小模型上,也能跑出比较好的结果.
	- LLM擅长推理,但是天然具有概率性,因此存在固有问题,harness就是要将LLM封装成一个可靠,可控,可持续演进的Agent系统:
		- 输出不稳定
		- 上下文有限
		- 缺乏长期经验积累
		- 缺少权限,安全,审计工程能力
	- 上下文水位到达50%以上,codeagent会降智.harness能解决上下文管理,subagent调度问题,所以才要agent分层\流程化\设计harness流水线(类似我们软件的CI),本质上,harness流水线就是一个软件系统.
		- 规划和执行:harness负责任务规划,调度工具调用和异常恢复.(harness会有规范的文档输出要求,每个阶段输出记录该阶段的执行结果,作为异常恢复的基础)
		- verification(关键周期的拦截和检查):验证闭环输出结果(以patch sets合入的场景为例,实际完成一个patch sets合入工作,要经历多个步骤:环境的准备(patch来源,仓库地址,编译环境...)->深度阅读patch和仓库,制定最终合入规则,根据patch依赖关系和patch风险性确定各个patch是否要作为编译点)->逐个patch合入,又有经历am->conflict解冲突->build->解决编译错误->只有编译成功了才能进入下一个patch的合入阶段.在这个场景中,就严格要求我们记录每个步骤的执行结果,以及执行状态,通过读取harness的执行状态,结合我们之前制定好的状态机规则,确定下一步的状态,比如解冲突的话,只有从conflict->pass的时候,才能执行下一步build.
			- 验证:LLM无法确保一次性完成任务,所以要经历Generate->verify->repair->verify的循环验证来保证任务执行的质量
		- subagent+workflow:每个任务创建独立的上下文与工作区,避免相互污染

# 1. 减少上下文消耗

agent每次写代码->跑测试->报错->修复->再报错的循环中,每一次失败的日志,diff,工具调用结果都消耗宝贵的上线文窗口.

解决办法:
- 主agent负责任务目标,约束条件,背景信息,**验收标准verify**(把控整体流程),原则:协调者绝不写代码,只管规划,委派,汇总
- 子agent负责:记录关键执行摘要->更新执行结果->变更清单(专注一件事),原则:每次从干净的上下文开始,主agent和subagent之间通过artifacts传递信息(持久化产物),其他内容互不干扰.,子agent干完就释放


可以列举一下,我在patch merge的skill中,列举出来的作为harness的几种场景

planner和builder的拆分
planner和builder在单智能体做的职责太多，会导致上下文爆炸，尤其是在长任务当中，任务非常多，会导致上下文爆炸。
解决方案：planner拆分为product, design, arch, builder拆分为testcase和builder
按照实际开发当中的职责分别去委托到不同的Agent当中，并且拆分彼此的上下文，进而避免上下文爆炸导致的生成质量下降的问题。

# 2. 事前拦截成本低于事后修复

以patch merge SKILL为例,如果无脑合入,等到最后几十个path合入完再编译校验,很大概率是编不过的,那么事后得不断往前查找是哪个patch出问题,不断验证解决,最终上下文爆炸

最好的办法是小步编译验证,然后验证的时候分析错误->改正->验证,一般1-3轮就收敛了.

还有一个事前拦截的点,就是根据经验,给ai一个问题解决矩阵,减少ai试错

这里典型的例子就是解冲突conflict的时候,decision_table.md里面

沙箱保护:
- 容器内根文件系统只读
- 给CPU,进程,内存使用率进行限额
- 不向沙箱内注入任何宿主机环境变量
- 执行记录要完整写入审计日志中,既能时候追溯定责,也能为模型优化沉淀数据,这里patch merge skill是个很好的例子,新版本已经把conflict记录,编译和编译报错记录全部记下来了,所以一旦发现ai有修改不合理的地方,我都可以第一时间直接查看日志记录,分析原因.(CI也是这么干的)
- block:制定红线规则

# 3. 状态恢复

以一份JSON形态的元数据作为状态恢复的依据(这里可以贴如artifacts的元数据结构)

生命周期hook:是harness把强规则落地的关键机制,设计哲学是:不去改写模型的推理循环,而是在循环的关键时机插入钩子,做拦截,注入,记录(这里也可以在patch merge找到对应的内容),以此为例,在一些关键时机加入hook:
- prereasoning:注入上下文.把最新state记录下来,重新执行任务是,按需加载记忆
- posttoolcall:结果校验与状态更新
- 记忆回写:将本次任务的执行结果和关键要点提炼出来,可以作为持续演化skill的依据

# 4. 让ai自动学习,自动优化skill(后续工作)

这个是后续的工作,比如我们在conflict和build解冲突的时候,针对每个冲突内容和冲突原因,可能都能指导我们后面skill的工作,所以冲突解决的知识库足够的话,我们skill最后进行patch合入的能力也会越强,可以让ai在解冲突的时候,记录一些有价值的方法,存到规则库中.

# 解剖怎么让skill动态根据任务和场景,生成执行计划

 怎么确保按执行计划执行:

1. 第一层：TodoWrite 跟踪                                                                                                                                                                                  
                                                                                                                                                                                   
     writing-plans 生成的计划用 - [ ] checkbox 格式，AI 执行时用 TodoWrite 逐项打卡——这是 Commitment（承诺） 说服原则：                                                             
     先公开声明任务列表，再逐项完成，违反一致性会产生心理压力

我们可以参考他的做法，生成的plan用`- [ ]`包住，plan可以实现sub skill的热插拔，比如，plan可以选择：

- [ ] 查找需要的patch
- [ ] 依赖库搜索
- [ ] patch深度搜索，并生成merge计划表，checkpoint
- [ ] 逐个patch执行patch-merge，每个patch必须检测到state pass后才能执行下一个
- [ ] review
- [ ] 输出产物

热插拔体现在，plan也可以根据是否有依赖库，是否已经提供了patch，生成另一份plan：

- [ ] patch深度搜索，并生成merge计划表，checkpoint
- [ ] 逐个patch执行patch-merge，每个patch必须检测到state pass后才能执行下一个
- [ ] review
- [ ] 输出产物

2. 第二层:subagent 隔离 + 两阶段 review 

   真正确保执行质量的核心机制：                                                                                                                                                   
                                                                                                                                                                                    
     每个 Task:                                                                                                                                                                     
       1. 派 implementer subagent（全新上下文，只看当前 task 文本）                                                                                                                 
       2. 派 spec-reviewer subagent（验证是否按 spec 做，防偷工减料）                                                                                                               
       3. 派 code-quality-reviewer subagent（验证代码质量，防 over-engineering）                                                                                                    
       4. 任一 review 不通过 → implementer 修 → 再 review                                                                                                                           
                                                                                                                                                                                    
     spec-reviewer 的 prompt 里甚至写了：                                                                                                                                           
                                                                                                                                                                                    
     │ CRITICAL: Do Not Trust the Report                                                                                                                                            
     │ The implementer finished suspiciously quickly. Their report may be incomplete, inaccurate, or optimistic.                                                                    
                                                                                                                                                                                    
     这就是不信任单个 AI 的自汇报，用独立 subagent 做交叉验证。相当于你们 execution_log 的"独立读结果"而非"信任 AI 报告"。                                                          
                                                                       

怎么规定生成执行计划的？

   writing-plans/SKILL.md 定义了极严格的计划格式：                                                                                                                                
                                                                                                                                                                                    
     a) 强制 header：                                                                                                                                                               
                                                                                                                                                                                    
     # [Feature Name] Implementation Plan                                                                                                                                           
     > **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development                                                                                     
     **Goal:** [One sentence]                                                                                                                                                       
     **Architecture:** [2-3 sentences]                                                                                                                                              
     **Tech Stack:** [Key technologies]                                                                                                                                             
                                                                                                                                                                                    
     b) 每步粒度 = 2-5 分钟：                                                                                                                                                       
                                                                                                                                                                                    
     - "Write the failing test" - step                                                                                                                                              
     - "Run it to make sure it fails" - step                                                                                                                                        
     - "Implement minimal code" - step                                                                                                                                              
     - "Run tests" - step                                                                                                                                                           
     - "Commit" - step                                                                                                                                                              
                                                                                                                                                                                    
     c) 禁止占位符（这是红线）：

                                                                                                                                                                                   
     这些是 plan failures — 绝不能写：                                                                                                                                              
     - "TBD", "TODO", "implement later"                                                                                                                                             
     - "Add appropriate error handling"                                                                                                                                             
     - "Write tests for the above"（没有实际测试代码）                                                                                                                              
     - "Similar to Task N"（必须重复代码）                                                                                                                                          
                                                                                                                                                                                    
     d) 自检环节：                                                                                                                                                                  
                                                                                                                                                                                    
     写完计划后，AI 必须 self-review 三项：                                                                                                                                         
                                                                                                                                                                                    
     1. Spec coverage — 每个 spec 需求是否有对应 task                                                                                                                               
     2. Placeholder scan — 搜索占位符                                                                                                                                               
     3. Type consistency — 前后 task 的类型签名是否一致                                                                                                                             
                                                                                                                                                                                    
     本质上，writing-plans 是在把 spec 变成 subagent 可以独立执行的原子任务——每个 task 自包含、有完整代码、不需要读其他 task。
